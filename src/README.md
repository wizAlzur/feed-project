# Подготовка производственного задания на партию комбикорма

Программа проверяет заявку, выбирает действующую утверждённую рецептуру,
рассчитывает потребность, проверяет запасы и формирует производственное задание.
После явного утверждения технологом повторяет проверку и резервирует сырьё
для всей партии. При отказе указывает причину возврата заявки.

Python 3.9 или новее. Проверено на Python 3.9.6 и 3.12.14.
Используется только стандартная библиотека.

## Обработка заявки

Все команды ниже выполняются из папки `src`. В `examples/workflow.json`
содержатся десять списков, соответствующих сущностям логической модели:
`products`, `recipe_versions`, `components`, `recipe_composition`, `requests`,
`production_tasks`, `task_items`, `stock_lots`, `reservations`, `reservation_items`.
Каждая запись - словарь с теми же атрибутами, что на ER-диаграмме.
Количества и доли в JSON задаются строками, незаполненные необязательные даты
и причина возврата - `null`.

Пример содержит заявку 1 на 1000 кг. Для продукции есть истёкшая версия 1,
действующая утверждённая версия 2 и черновая версия 3. Выбирается версия 2
с долями 60%, 25% и 15%. Дата обработки передаётся явно для воспроизводимости.

Сформировать черновик, сохранив результат отдельно:

```bash
python3 main.py --data-file examples/workflow.json --request-id 1 --processing-at 2026-10-31T10:00:00 --output draft.json
```

Ожидаемый вывод до строки с именем выходного файла:

```text
Заявка 1: Задание сформировано, ожидается утверждение технологом.
Статус заявки: processing
Задание 1: рецептура 2, статус draft
Продукция: 1; масса партии: 1000 кг; срок: 2026-11-03
Компонент 1: 600 кг
Компонент 2: 250 кг
Компонент 3: 150 кг
```

Подтвердить утверждение технологом и подготовить задание:

```bash
python3 main.py --data-file draft.json --request-id 1 --processing-at 2026-10-31T10:05:00 --approve --output ready.json
```

Ожидаемый вывод до строки с именем выходного файла:

```text
Заявка 1: Задание готово к передаче в производство, сырьё зарезервировано.
Статус заявки: ready
Задание 1: рецептура 2, статус ready
Продукция: 1; масса партии: 1000 кг; срок: 2026-11-03
Компонент 1: 600 кг
Компонент 2: 250 кг
Компонент 3: 150 кг
Резерв 1:
Партия сырья 101: 400 кг
Партия сырья 102: 200 кг
Партия сырья 201: 250 кг
Партия сырья 301: 150 кг
```

Первый компонент распределён между двумя складскими партиями.
Заблокированная партия 103 не используется. Можно сразу выполнить команду
с `examples/workflow.json` и `--approve`, минуя сохранение черновика.

Показать возврат из-за изменения запасов после утверждения:

```bash
python3 main.py --data-file examples/workflow.json --request-id 1 --processing-at 2026-10-31T10:00:00 --approve --stock-update-file examples/stock_after_approval.json --output returned.json
```

Первичная проверка успешна. В новом складском снимке доступно только 500 кг
первого компонента при потребности 600 кг. Ожидаемый вывод до строки с именем файла:

```text
Заявка 1: Заявка возвращена на доработку.
Статус заявки: returned
Причина: Компонент 1: не хватает 100 кг.
Задание 1: рецептура 2, статус returned
Продукция: 1; масса партии: 1000 кг; срок: 2026-11-03
Компонент 1: 600 кг
Компонент 2: 250 кг
Компонент 3: 150 кг
```

Частичного резерва нет, `approved_at` очищено. Снимок содержит только
`stock_lots`, `reservations`, `reservation_items` и заменяет эти три списка
перед повторной проверкой. Связанные заявки и задания должны уже присутствовать
в основном файле. Без отдельного снимка повторная проверка использует текущее
состояние складских списков в памяти.

Повторный запуск готового задания:

```bash
python3 main.py --data-file ready.json --request-id 1 --processing-at 2026-10-31T10:10:00
```

Первая строка: `Заявка 1: Задание уже подготовлено, существующий резерв сохранён.`
Новые задания и резервы не создаются.

Правила обработки:

- Масса положительная, до 1 000 000 кг и трёх дробных знаков; продукция есть
  в справочнике; срок выпуска не раньше даты обработки. В новой/возвращённой
  заявке `null` вместо обязательного значения приводит к возврату с причиной.
  Нарушение структуры записей или связей в справочниках считается ошибкой данных.
- Версия рецептуры утверждена и действует на дату обработки; обе границы
  периода включительные, `valid_to: null` означает отсутствие верхней границы.
  Если подходящих версий нет или больше одной, заявка возвращается.
- `--approve` передаёт решение технолога. Без него нет утверждения и резерва.
- Резерв создаётся целиком по допущенным партиям в порядке записей файла,
  с учётом действующих резервов других заданий. `quantity_kg` не уменьшается.
- Возвращённая заявка обрабатывается заново с пересчётом позиций и новым
  утверждением. Отменённый заголовок резерва того же задания переиспользуется.
- Готовые заявки и их активные резервы не изменяются этой программой.
  Отдельные процессы отмены, выпуска продукции и редактирования готовой заявки
  не реализованы; сохранённое готовое состояние не следует править вручную.

Функции получают данные через параметры; `process_request()` возвращает
`data` (новое состояние), `outcome` и `availability`. Исходные записи не меняются.
Результат хранится в памяти; для записи JSON укажите `--output` с именем,
отличающимся от входных файлов. Запись заменяет выходной файл только после
успешного формирования JSON. Работа последовательная, без одновременной записи
из нескольких процессов; СУБД на этом этапе не используется.

Возврат заявки, ожидание утверждения и успех имеют код выхода 0.
Некорректный файл/связи/числа - 1, неверное сочетание аргументов - 2.

## Отдельный запуск расчёта

```bash
python3 main.py 1000 examples/recipe_composition.json
```

В примере три компонента с долями 60%, 25% и 15%. Ожидаемый вывод:

```text
Потребность в компонентах:
Компонент 1: 600 кг
Компонент 2: 250 кг
Компонент 3: 150 кг
```

Файл содержит строки сущности «Состав рецептуры»: `recipe_id`,
`component_id`, `share_percent`. Компоненты не должны повторяться,
все строки должны относиться к одной версии. Утверждение и действие
версии на дату расчёта этот отдельный пример пока не проверяет.

Масса задаётся в кг строкой с точностью до 0,001 кг, больше нуля
и не больше 1 000 000 кг. Доли задаются строками с точностью до 0,0001%,
каждая больше нуля и не больше 100; их сумма должна равняться 100%.
В числах используется точка. Значения с лишними дробными знаками отклоняются.
Расчёт выполняется через `Decimal`, без округления отдельных компонентов.

`calculate_requirements()` принимает массу и проверенный состав одной версии,
возвращает список с `component_id` и `required_quantity_kg` типа `Decimal`.
При ошибке выбрасывает `ValueError` с причиной. Команда выводит причину
и завершается с кодом 1; исходные данные при расчёте не изменяются.

## Проверка обеспеченности

```bash
python3 main.py 1000 examples/recipe_composition.json --stock-file examples/stock.json
```

Ожидаемый вывод:

```text
Потребность в компонентах:
Компонент 1: 600 кг
Компонент 2: 250 кг
Компонент 3: 150 кг
Проверка обеспеченности:
Компонент 1: требуется 600 кг, доступно 550 кг, дефицит 50 кг
Компонент 2: требуется 250 кг, доступно 300 кг, дефицит 0 кг
Компонент 3: требуется 150 кг, доступно 150 кг, дефицит 0 кг
Партия не обеспечена сырьём.
```

Складской файл содержит три списка с полями сущностей ER:

- `stock_lots`: `stock_lot_id`, `component_id`, `quantity_kg`, `admission_status`;
- `reservations`: `reservation_id`, `task_id`, `created_at`, `status`;
- `reservation_items`: `reservation_id`, `stock_lot_id`, `reserved_quantity_kg`.

В примере из 700 кг первого компонента 150 кг занято действующим резервом
задания 10. Ещё 100 кг заблокированного сырья не учитываются. Резерв второго
компонента отменён, поэтому все 300 кг доступны. Третьего компонента ровно 150 кг.

`check_availability()` получает результат расчёта потребности и эти три списка.
Возвращает словарь с общим признаком `can_fulfill` и списком `components`,
где для каждого компонента указаны `component_id`, `required_quantity_kg`,
`available_quantity_kg`, `shortage_quantity_kg`. Все количества имеют тип `Decimal`.
Дефицит является результатом проверки; команда завершается с кодом 0.
Некорректные данные приводят к `ValueError`, команда завершается с кодом 1.

Остатки задаются строками в кг до трёх дробных знаков, потребности и количества
резервов - до девяти. Остатки неотрицательные, потребности и резервы положительные;
каждое входное количество не больше 1 000 000 кг. `created_at` записывается
строкой даты и времени ISO 8601. Статусы допуска: `pending`, `admitted`, `blocked`;
статусы резерва: `active`, `cancelled`. У каждого резерва должна быть хотя бы
одна позиция. Повторяющиеся ключи и отсутствующие связи отклоняются.

Для повторной проверки существующего задания можно передать его ID:

```bash
python3 main.py 1000 examples/recipe_composition.json --stock-file examples/stock.json --task-id 10
```

Тогда собственный резерв задания 10 исключается из занятого количества.
В примере доступно 700, 300 и 150 кг, дефициты равны нулю, последняя строка:

```text
Партия обеспечена сырьём.
```

Собственный резерв продолжает учитываться при проверке превышения складского
остатка всеми действующими резервами. Проверка не создаёт и не отменяет резервы,
не списывает сырьё и не меняет переданные записи. Поиск связанных записей
выполняется последовательным просмотром списков.

## Проверки

```bash
python3 test_requirements.py
python3 test_availability.py
python3 test_workflow.py
```

Проверяются расчёт и точность малых количеств, ошибки данных, ключи и связи,
все дефициты, допуск сырья, действующие и отменённые резервы, исключение
собственного резерва и сохранность исходных данных при успехе и отказе.
Проверки полного процесса также охватывают выбор версии по дате, утверждение,
распределение полного резерва по партиям, изменение запасов, повторную обработку,
возврат и исправление заявки, переиспользование отменённого заголовка, точность
малых количеств, ключи и связи десяти сущностей, JSON и команды запуска.
